# DIMS-STD-0008 — Canonical DOME Module Page Standard v1.0

Status: Governed preview standard
Governance: TASK-0102 / TASK-0123 reconciliation
Production promotion: prohibited until user review and sign-off

## Purpose
Establish one visual, theological, functional, responsive, and routing architecture for every primary DOME module page. TETELESTAI™ is the reference implementation. Once accepted, the standard is propagated across all eight governed modules.

## Canonical page hierarchy
1. Global DOME Navigation
2. Module Hero
3. Module Identity
4. Operational Workspace
5. Persistent DI² intelligence access where applicable

## Visual hierarchy
- Global DOME Navigation: deep navy.
- Module Hero: Dominion1st royal blue; visually distinct from navigation.
- Module Identity: a clearly different lighter/brighter blue, not merely a small tonal shift from the hero.
- Gold: structural accent/divider/emblem detail, not identity-label text.
- Identity labels and content: white; labels bold.
- Operational workspace: light neutral in day mode and governed dark equivalent in night mode.
- Day/night: compact sun/moon toggle. Do not duplicate Light/Dark text controls when the compact toggle is present.

## Module hero requirements
Each primary module hero must include:
- DOME™ + plain-English operational category.
- Canonical module name.
- Governed emblem/icon where one exists.
- Emblems must remain fully within the viewport at desktop and mobile sizes.
- Emblem motto/subtitle belongs inside the emblem when the design uses a circular seal.
- No unexplained or nonfunctional controls.

## Module identity requirements
Every primary module must explicitly present these four elements:
1. **Meaning / Origin** — Greek, Hebrew, biblical-language, or coined-term origin.
2. **Why This Name** — concise explanation of why the term was chosen and how the meaning fits the module's work.
3. **Scripture** — governing Scripture written out, with translation identified.
4. **Function** — explicitly labeled `Function:` and written in plain operational language.

Do not use the implementation term `surface` in user-facing module identity descriptions. Prefer workspace, module, environment, briefing, library, or direct functional wording as context requires.

## Ratified OrEl™ identity principle
OrEl™ remains the module name. It is a Dominion1st coined term, not presented as a biblical compound word.
- `Or` / Hebrew ʾôr: light.
- `El`: God.
- Intended concept: God-light / light of God; illumination moving into faithful creative expression.
- Functional progression: illumination → understanding → expression → writing/creation.
- OrEl™ should therefore be described as an illumination and creative-expression workspace, not merely a generic text editor.

## TETELESTAI™ reference implementation requirements
- Cross emblem responsive on mobile and desktop.
- `IT IS FINISHED` contained inside the circular emblem.
- Identity area uses the distinct third blue.
- Identity labels bold white.
- Existing authenticated Supabase Projects/Tasks loading remains intact.
- Existing System RAC/database values remain intact.
- RAC/priority presentation must use the approved circular color-coded visual system; do not substitute the older horizontal segmented bar.
- Preserve project/task deep links and Add/Edit behavior.

## DOME Home
The phrase `See. Command. Steward.` is not ratified and must be replaced before production. Home-page copy and hierarchy must align with the current DOME architecture and avoid creating competing system identities.

## Mission Control
- Canonical page identity remains `Mission Control` unless separately governed.
- Do not present `Execution Command Center` as a competing page/system identity.
- Do not redefine DOME as `Dominion1st Operations & Mission Environment`.
- Supporting cards should describe Mission Control functions without creating a second command-center name.

## DSCC / System Health
- Canonical system identity remains `DSCC — Dominion System Command Center`.
- `System Health` is a DSCC function, not a replacement identity.
- Navigation may clarify the relationship as `DSCC — System Health & Command` after route/content reconciliation.

## Routing standard
The canonical route registry remains the navigation source of truth, but internal page links must also resolve to current canonical destinations.
- Repair stale internal links in DSCC, EKKLĒSIA/Marriage1st, Institutional Queue, Mission Control, Blueprint, and other recovered pages.
- Current navigation must not route users to construction-era pages when a canonical current destination exists.
- Legacy URLs may remain as governed aliases/history but must not masquerade as current destinations.
- Mobile Navigate drawer must allow full vertical scrolling to every registered destination.

## Acceptance gate
Before production promotion:
- Desktop visual review.
- Mobile visual review.
- Module identity consistency review.
- Current-route/internal-link integrity review.
- TETELESTAI authenticated data load.
- TASK/project deep links.
- Add/Edit behavior.
- Circular RAC presentation.
- Day/night behavior.
- DI² placement/behavior.
- Explicit user sign-off.
