**Date:** 2026-08-10

## Purpose

Convert the completed repository audit, live Supabase audit, historical-lineage audit, Google Drive evidence-gap closure, seven-module architecture, and governing synchronization policy into a controlled modernization program for the DOME application.

The objective is **not** to rebuild DIMS from scratch. The objective is to converge, secure, modernize, and integrate mature DMS/DIMS/DIMS-v3 capabilities into one coherent DOME application under **EBYC — Extend Before You Create**.

## Governing target state

- **DOME:** See & Command
- **Seven Modules:** Work & Operate
- **DI:** Understand & Connect
- **KUBERNĒSIS:** Govern & Orchestrate
- **Administration/System:** Configure & Govern
- **VAULT/Repositories:** Preserve & Recover

Canonical modules: GEGRAPTAI™, EKPOREUMA™, TETELESTAI™, OrEl™, YARATHĒKĒ™, SHAMAR™, OIKONOMOS™. Dominion1st Intelligence™ is a governed cross-module layer, not an eighth module.

## Non-negotiable doctrine

1. EBYC — Extend Before You Create.
2. Convergence Without Erasure.

4. No “Newest File Wins.”

## Phase 0 — Baseline freeze & authority control

Resolve authority conflicts that affect implementation: Canonical Artifact Register duplication, ADR/standard status, Enterprise Asset IDs, Cloudflare/Netlify production roles, and backup/restore confidence. No destructive archive/reorganization before authority and restore confidence are established.

## Phase 1 — Stabilize & Secure — CRITICAL

### 1.1 Supabase security
- Verify backup/restore procedure.
- Remove unconditional public ALL access from `asset_registry`, `peace_safety_briefs`, `projects`, `sync_log`, `tasks`, and `teachings`.
- Establish least-privilege role-based policies.
- Review broad authenticated ALL policies.
- Harden database function search paths.

### 1.2 Reproducible database
- Convert captured baseline into replayable migrations.
- Source-control constraints, indexes, functions, triggers, grants and RLS.
- Add schema drift checking.

### 1.3 OrAI hardening
- Add authentication/authorization, rate limits, quotas, request validation, safe errors, observability and prompt/model versioning.
- Remove misleading offline current-intelligence fallback.
- Disable autonomous AI “Now Word” generation.

### 1.4 Runtime truthfulness and stale schema cleanup
- Compare every frontend table reference to live Supabase.
- Resolve stale references such as `briefings`, `resume_points`, and `system_snapshots` where they no longer match backend reality.
- Replace unsupported operational/live claims with verified state.

### 1.5 Production/archive separation
- Stop publishing repository root.
- Establish dedicated build/output directory.
- Exclude ZIP archives, audits, test pages, historical variants and metadata exports from production output.

**Phase 1 completion gate:** security, database reproducibility, AI governance, schema truthfulness and production/archive separation must all be verified.

## Phase 2 — Unified DOME application foundation — HIGH

Build one authenticated application shell with seven module routes, shared auth/data/validation/error/logging services, persistent DI affordance, KUBERNĒSIS orchestration, Administration/System separation, and preserved VAULT/repository services.

Visual doctrine: DOME home remains circular/orbital as the command metaphor; module interiors use grids, tables, editors, libraries, timelines, forms and intelligence views as appropriate. Mobile reorganizes information rather than shrinking the desktop orbit.

## Phase 3 — Shared domain & provenance foundation — HIGH

Establish stable identities, record relationships, provenance, attribution, versioning, audit events, approvals, freshness, permissions, synchronization evidence and Enterprise Asset linkage.

## Phase 4 — Module migration & extension

1. **TETELESTAI:** relationships, owners, dependencies, milestones, recurring work, history, server-side filtering/pagination, board/list/calendar, DI exceptions.
2. **OrEl + YARATHĒKĒ:** consolidate competing teaching implementations while preserving independent domain authority; add versioning, approvals, Scripture/lexicon links, curriculum, research sources, media and publishing.
3. **EKPOREUMA:** human-authored records, Scripture/source anchors, discernment/testing, lifecycle, archive, testimony/fulfillment, MARTUREŌ witness/accountability.
4. **GEGRAPTAI:** recover DDBB AutoBuilder behavior; build evidence-linked cross-module daily briefing, continuity, citations, review, action extraction and preservation.
5. **SHAMAR:** governed source registry, freshness, watchpoints, thresholds, strategic threats, prophetic/biblical watch context, ownership, mitigation, escalation and ministry impact.
6. **OIKONOMOS:** extend existing backend into organizations, assets, subscriptions, contracts, property/legal references, stewardship dashboards, renewals, tighter access and DI reminders/anomalies.

## Phase 5 — Dominion1st Intelligence™ foundation

DI provides permission-aware search, retrieval, continuity, source-backed synthesis, stale/conflict detection, exception monitoring, watch intelligence, teaching/content relationships, stewardship context, persisted intelligence products, human-reviewable recommendations, and proactive priorities/reminders/accountability.

First production use case: an evidence-linked GEGRAPTAI daily executive briefing assembled from all seven modules with source IDs, freshness, verification state, action recommendations and links to TETELESTAI work.

## Phase 6 — Automation, synchronization & operating maturity

Programmatically implement the ratified synchronization policy where authorized; modernize Drive Inventory/DDIS into repository intelligence; add real health checks, sync/job status, deployment versioning, restore tests, publishing integrations and advanced cross-module automation.

## Codex execution model

Give Codex one controlled work package at a time. For each task it must read governing architecture/audits, apply EBYC, state planned changes, preserve provenance, remain within scope, run tests/checks, report changed files/migrations/security implications/blockers, and avoid external production changes unless specifically authorized.
